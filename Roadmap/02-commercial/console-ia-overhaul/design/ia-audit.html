Golden Beans · information architecture audit

Fifteen sections, four bolted-on links, and no object model

You asked where the nav items should go. The honest answer is that the question can't be answered one item at a time, because the product has no unit of work — a single feature is spread across five URLs, three of which ask you to edit the address bar by hand. Fix the object model and the navigation falls out of it. This audit reads every surface that exists on main today and places all nineteen.

01

Your three questions, answered first

The miyagisanchez / miyagisanchezmarketplace breadcrumb — real or invented?
Invented. My mistake.

In Flagsmith those are real: Organisation, then Project. In Golden Beans there is no organisation layer at all. getUserProjects(user.id) returns a flat list of projects a user is a member of, each with a slug and a role — that's it. I copied Flagsmith's two-level breadcrumb without checking whether the second level existed in your data. It doesn't.

What it should be: one project switcher. Golden Beans is single-tenant-per-project, so the top bar names the project you're in and lets you change it. Nothing above it, because there is nothing above it.

Am I proposing you build an org layer? No. Multi-project accounts already work (projects.length > 1 is handled in the shell today). An org tier would be a data migration in exchange for a breadcrumb, and you have one user with one project.

Is the prototype what I'd see at /app/flags/miyagisanchez?
No — and the gap is exactly what you're now asking me to fix.

Your real page is wrapped in ProductShell: the logo, Home, Sections, Connect, Agent notes, a project signal chip, and the AgentRail down the side. My prototype threw all of that away and drew Flagsmith's chrome instead, so it showed you a flags console that couldn't navigate anywhere. That's the same sin as the page it replaced — designing one screen as if it were the whole product.

It also still renders FlagManager's authoring stack underneath the list, which is why the JSON box is on your screen no matter what the console gate says.

Why isn't the features list truncated?
Fair hit — but truncation is the wrong fix.

Truncating 42 rows to 15 gives you 15 rows that say the same thing. 40 of the 42 are identical: never turned on, in any environment, by anyone. They carry no information individually and a lot of information collectively.

The standard heuristic here isn't pagination, it's summarise the uniform, expand the exceptional. Default view: the 2 that are on, the 1 that's off, and one row that reads "40 features have never been turned on here" with a disclosure arrow. Three rows, one screen, no scroll. Pagination at 15 only applies once you open that row — which is the rare case, not the default.

What is actually on the screen today

Seventeen destinations, presented as one flat list inside a <details> disclosure, ordered by the sprint that happened to build them. There is no grouping, no frequency signal, and no hierarchy — which is precisely what you described: bolted on as each feature landed.

Two of them instruct you to edit the URL. Funnel and Impact are keyed by feature, and the inventory has no feature picker, so it emits a literal placeholder:

href: /app/funnel/miyagisanchez/your-feature-key
description: "swap the feature key in the URL"

That string is exported as DEFAULT_FEATURE_HINT and shared between the nav and the home page, with a comment saying a picker will land eventually. That is the incoherence you hit. It is not a copy problem — it's a missing object.

03

The finding underneath every other finding

Before any nav can be designed, the product needs a noun.

Golden Beans is a growth engine: you ship a thing, you switch it on for some people, you watch whether it moved the number. That is one loop about one object — a feature. But the product has no page for a feature. It has five pages that each hold one aspect of one:

This is the same defect as the flags page, one level up. The flags page showed the storage model instead of the job; the navigation shows the route table instead of the work. Both were built by adding a link per sprint.

One caveat, stated rather than glossed. There are two registries today: TARS features (measured, keys like setup_guide) and flag definitions (switched, keys like checkout.stripe_enabled). They are not the same table and not the same naming convention. Unifying them is a data decision, not a design one, and it is yours to make.

The IA below works either way — a feature page shows the tabs it has data for, and says plainly when a feature is measured but not switched, or switched but not measured. That honesty is useful on its own: it tells you which of your 42 flags nobody is measuring.

04

The content strategy: four questions, four destinations

Everything a person opens Golden Beans to do is one of four questions. Nav items are answers to those questions, not names of subsystems.

Question 1

“Did anything need me?”

The front door. Headline numbers, what moved, what broke, what's waiting. You should be able to close the tab from here on a good day.

→ Today · daily
Question 2

“Is the thing I shipped working?”

Funnels, impact on the North Star, journeys, drills. Measurement, always about a feature or about the whole project.

→ Measure · weekly
Question 3

“Change something.”

The levers: switch a feature on or off, run an experiment, roll something back. The only place in the product where an action has consequences for customers.

→ Ship · weekly, and in an incident
Question 4

“Wire it up.”

Connect your agent, get your keys, point your webhooks, share a report. Done once, changed rarely, and never while you're trying to work.

→ Setup · once, then almost never

Four destinations, not seventeen. The ordering is not aesthetic — it is frequency of use, which is the only defensible way to rank nav items and the standard every mature console follows. Setup is last and quietest because a nav item you need once should not compete daily for attention.

The one rule that keeps it from re-inflating

Every new surface must answer one of those four questions, and it joins that section's rail. It does not get a new top-level item. If it genuinely answers none of them, that is the signal to question the surface, not to extend the nav. This is the rule the current inventory never had — which is why fifteen entries accumulated without anyone deciding to have fifteen.

  • Tier 1 — the project. One switcher in the top bar. Everything below it belongs to that project. Also here: search (⌘K, which is how anyone with 42 features actually navigates), help, and your account menu. That's four controls, and every one of them is global rather than section-specific — which is the test for whether something belongs in a top bar.
  • Tier 2 — the four questions. Today · Measure · Ship · Setup. Never more.
  • Tier 3 — the rail. What's inside the section you picked, plus any scope that section needs. Flags need an environment; the rail is where that lives, because it scopes this section and nothing else. Putting it in the top bar would imply it governs Measure and Setup too.

    • Why ⌘K matters more than any menu here. With 42 features, 3 environments and a dozen surfaces, the fastest path to anything is typing its name. Every console at this size ships one, and it is the single highest-leverage nav element you could build — it makes the depth of tier 3 free, because nobody has to walk the tree to get there.

    On merging the four credential surfaces

    Golden Beans currently has four separate pages that issue secrets: API keys, flag credentials, agent write keys, and the connector token. Nobody thinks “I need a flag credential” — they think “I need to give something access”. One Keys page, with a column for what each key may do and a filter, is the standard shape and removes three nav items. The permission boundaries don't change: each row still enforces its own owner check exactly as its page does today.

    07

    Connect — you were right, and it's nearly built

    Confirmed broken, in two distinct ways

    One: it's a marketing page wearing product chrome. /install imports Nav and Footer from components/landing/. Clicking Connect from inside your dashboard drops you out of the product and onto the website, with the website's header, a sales headline, and a footer.

    Two — and this is the real one: it hands you the wrong token.

    app/install/page.tsx:31   await getActiveConnectorUrl(DEMO_PROJECT_SLUG)

    Signed in as you, on your own project, the Connect link gives you the demo project's connector URL. Not yours. Your instinct that Golden Beans can't really be connected that way was right — that URL points at demo data.

    The good news is that what you asked for already exists. You described exactly this: a signed-in experience where users get their personal URL with their own token baked in, ready to paste into claude.ai/customize/connectors. That page is written:

    app/app/onboarding/[projectSlug]/page.tsx:60   await getActiveConnectorUrl(projectSlug)

    It resolves your project's real, revocable token. It is unreachable from any navigation, because the inventory marks it status: 'flow-only' and getProjectSurfaceLinks filters those out. The feature is finished and hidden.

    What Connect should be

  • Setup → Connect, inside the product shell. No landing Nav, no Footer, no sales headline. You are already sold; you signed in.
  • Your URL, your token, one copy button, and the Add-to-Claude deep link right beside it — the flow you named. The token is scoped to the project in the switcher, so switching project switches the URL, which is the behaviour anyone would assume.
  • Connection state, not instructions. “Connected · last used 2 hours ago” or “Not connected yet”. A setup page that can't tell you whether setup worked is a document, not a tool.
  • The SDK snippet moves to docs, with one link from here. It is for the engineer wiring up data-in, not for the operator connecting an agent. Two audiences, two places — putting the npm install block on the same panel as your personal token is what makes that page feel like three products stapled together.
  • Setup shows a badge until it's done, then goes quiet. Standard progressive reduction: prominent while it's the most valuable thing you could do, demoted the moment it isn't.

    What this deletes

    A content strategy is only real if it removes things. This one removes more than it adds.

    • Thirteen top-level destinations become four, with everything reachable in at most three clicks or one ⌘K.
    • The Sections disclosure — the flat list of every route in the product.
    • Two nav items that instruct you to edit the URL, and the DEFAULT_FEATURE_HINT placeholder behind them.
    • Three of the four key-issuing pages.
    • Two of the three audit surfaces.
    • The Agent notes link to a crawler manifest.
    • The marketing header and footer from inside a signed-in session.
    • The demo project's token being handed to real users as if it were theirs.

    Two things get built, and both are small: the feature page that holds the switch, the funnel, the impact and the history together — which is mostly re-pointing routes that already render — and ⌘K, which is a filter over a list you already have.
